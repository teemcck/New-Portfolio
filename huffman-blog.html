Canonical Huffman File Compressor

Overview of Huffman Coding

Huffman Coding is a process commonly used for lossless data compression. In the context of compression, Huffman Coding works by parsing symbols present in a data source and mapping them to variable-length codes which it substitutes in an encoded output. More frequently occurring symbols are assigned shorter codes, while less frequently occurring symbols are assigned longer codes, reducing the overall size of the encoded data.

The term "symbols" is intentionally left abstract since different formats may define the units being encoded differently and with varying degrees of complexity. For example, a simple implementation may treat each byte of a file as a symbol.

What is Canonical Huffman Coding?

When compressing from a data source, it is important to include meta data to explicitly state or allow inference to the "codebook" used to compress the file. The codebook is responsible for storing which symbols map to which codes. For Huffman Compression, this requires us to format a header in one of the following ways:

  • Store the entire structure of the binary tree so codes can be reconstructed during decompression.
  • Store the codes in order of all possible symbols, using a predefined nullcode symbol for symbols that do not occur.

Both of these methods of sourcing the codebook for decryption are fine for large files, but can become costly for small files. When encrypted, small files have the potential of becoming larger if the size of the header is greater then the original size of the file (which would be common for encoding a large binary tree or array of codes).

Canonical Huffman is an adapation of conventional Huffman algorithms with the added step of standardizing the codes. This added standardization step occurs after we have constructed the Huffman Tree and have found the lengths of the codes, and before we build an indexable codebook.

Canonical Huffman codes follow these rules:

  • All codes of a shared length are assigned their values sequentially.
  • For codes of a shared length, order is determined by alphabetic value.

How is this implemented?

For the sake of this project being an educational delve into Huffman Coding, I define my symbols as being ASCII bytes. Apart from being able to be representing by small types like uint8_t, the real benefit of this selection of symbol is that there are \(2^8\) possibilities for symbols which keeps the data structures used in this project relatively small. When building a binary tree, we constrain our total number of leaf nodes to be less then \(2^8\). This is also the standard approach given in any textbook Huffman implementation

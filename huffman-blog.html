Canonical Huffman File Compressor

Overview of Huffman Coding

Huffman Coding is a lossless data compression technique that represents symbols using variable-length codes. More frequently occurring symbols are assigned shorter codes, while less frequently occurring symbols are assigned longer codes. By using shorter codes for common symbols, Huffman Coding can reduce the overall size of the encoded data.

Note that the term "symbol" here is intentionally abstract as the units being encoded depend on the data format. For example, a symbol could simply be a single byte in a file.

What is Canonical Huffman Coding?

When compressing from a data source, it is important to include meta data to explicitly state or allow inference to the "codebook" used to compress the file. The codebook is responsible for storing which symbols map to which codes. For Huffman Compression, this requires us to format a header in one of the following ways:

  • Store the entire structure of the binary tree so codes can be reconstructed during decompression.
  • Store the codes in order of all possible symbols, using a predefined nullcode symbol for symbols that do not occur.

Both of these methods of sourcing the codebook for decompression are fine for large files, but can become costly for small files. When compressed, small files have the potential of becoming larger if the size of the header is greater then the original size of the file (which would be common for encoding a large binary tree or array of codes).

Canonical Huffman is an adapation of conventional Huffman algorithms with the added step of standardizing the codes. This added standardization step occurs after we have constructed the Huffman Tree and have found the lengths of the codes, and before we build an indexable codebook.

Canonical Huffman codes follow these rules:

  • All codes of a shared length are assigned their values sequentially.
  • For codes of a shared length, order is determined by alphabetic value.

Algorithm Outline

This project implements a byte-oriented Huffman compressor and decompressor. It treats every input byte as a symbol in the range 0-255.

The encoder counts how often each byte appears, builds a Huffman tree, turns the tree depths into canonical codes, then writes a header and the encoded payload. The decoder canon reads the header, reconstructs those sameical codes, and uses them to recover the original bytes.

The command-line entry point is main.c. It accepts -e to encode or -d to decode, followed by the input file and target file respectively for both modes.

The encoding process collects the data from the file and passes it through a series of representations:

  1. Counting Bytes: count_frequencies() reads the input with fgetc. It uses an int for each result because fgetc must represent both every byte value and the special EOF value. Each byte's count goes into uint64_t frequencies[256]. The total input size is stored as uint32_t, which matches the four-byte size field in the file format. 
    
                        int symbol;

                        // Read bytes until EOF, counting each symbol and the total input size.
                        while ((symbol = fgetc(input)) != EOF) {
                            if (*total_symbols == UINT32_MAX) {
                                return EXIT_FAILURE;
                            }
                            ++frequencies[symbol];
                            ++(*total_symbols);
                        }
  2. Build a Huffman tree: we are able to forward the collected frequencies to a new function that may construct a "Huffman" tree. Huffman trees are built strictly using a bottom-up approach. Start by inserting elements, sorted by frequency from least to greatest, into a minheap. 
    
                        minheap heap = {0};
                        // Leave the caller with no tree on failure or empty input.
                        *root = NULL;

                        // Insert one leaf for each symbol that occurs in the input.
                        for (size_t symbol = 0; symbol < SYMBOL_COUNT; ++symbol) {
                            if (frequencies[symbol] != 0) {
                                // calloc initializes the child pointers to null on this platform.
                                huffman_node *leaf = calloc(1, sizeof(*leaf));
                                if (leaf == NULL) {
                                    release_heap_trees(&heap);
                                    return EXIT_FAILURE;
                                }
                                leaf->frequency = frequencies[symbol];
                                leaf->symbol = (uint8_t)symbol;
                                // At most 256 leaves are inserted into a 256-entry heap.
                                heap_insert(&heap, leaf);
                            }
                        }
    After building your minheap, you can repeatedly combine the two least frequent elements into internal nodes and reinsert them back into the tree. Continue this process until there is one final node, which is your root node. In this representation, all of the leaf nodes of our Huffman tree correspond to individual symbols. 
    
                        // Repeatedly combine the two least frequent trees into one parent.
                        while (heap.size > 1) {
                            // Allocate before removing children so failure cleanup can find them.
                            huffman_node *parent = calloc(1, sizeof(*parent));
                            if (parent == NULL) {
                                release_heap_trees(&heap);
                                return EXIT_FAILURE;
                            }
                            parent->left = heap_pop_top(&heap);
                            parent->right = heap_pop_top(&heap);
                            // Internal nodes represent the combined frequency of their children.
                            parent->frequency = parent->left->frequency + parent->right->frequency;
                            heap_insert(&heap, parent);
                        }
  3. Get code lengths: build_code_lengths walks the tree. A leaf's depth becomes that byte's code length. A one-symbol input is assigned a one-bit code so it still has a usable code. The tree is freed after its lengths have been collected.
  4. Limit lengths and create canonical codes: limit_code_lengths caps lengths at MAX_CODE_LEN (15) while preserving a valid prefix code. validate_code_lengths checks the result and counts codes at each length. The encoder then sorts (symbol, length) pairs by length and symbol value, and build_canonical_codes assigns the bit patterns. Canonical codes avoid storing the tree itself: both sides can derive the same codes from the lengths and ordering.
  5. Write the header and payload: The encoder rewinds the input to its starting position, writes the code lengths and original byte count, then reads each input byte again and looks up its code in huffman_code codebook[256]. bit_writer emits the code bits and pads the final output byte with zeros if needed.
